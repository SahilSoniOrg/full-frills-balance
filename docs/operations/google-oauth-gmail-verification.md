## OAuth setup and safe project/client selection

The requested scope is `https://www.googleapis.com/auth/gmail.readonly`. Google classifies it as a **restricted** Gmail scope. [Google Restricted Scopes](https://support.google.com/cloud/answer/13464325?hl=en)

For the current production build and verification, keep using `fiscalmoneymanger`: it is the project whose web, iOS, and Android registrations the live build uses. Google's submission guide allows selecting an existing project; Google's platform guidance calls for the appropriate Web, Android, and iOS client types, with Android clients tied to the package and signing certificate. [Submitting an app for verification](https://support.google.com/cloud/answer/13461325?hl=en) · [Google's Sign in with Google best practices](https://developers.google.com/identity/siwg/best-practices)

The Android Gmail authorization code reads `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID`; iOS additionally reads `EXPO_PUBLIC_GOOGLE_IOS_CLIENT_ID` ([implementation](../../src/services/email/gmailAuthorization.ts), [iOS URL-scheme configuration](../../app.config.ts)). For a future EAS production configuration, store only the matching **public OAuth client ID values** in those public environment variables. Google distinguishes the client ID from a client secret and notes that native and JavaScript apps are public clients that cannot securely keep secrets. Never commit actual secret credentials. [Google OAuth client guidance](https://support.google.com/cloud/answer/15549257?hl=en) · [Using OAuth 2.0](https://developers.google.com/identity/protocols/oauth2)

## Adding or configuring a Google Cloud project

Use this sequence when preparing a project for Gmail OAuth. For the current Play build, use `fiscalmoneymanger`; the separate `full-frills-balance-production` project is not wired into the shipped app.

1. **Choose the project deliberately.** Prefer the project whose OAuth client IDs are already in the production build. To create a new project, use Cloud Console's **Manage resources → Create project** flow. Choose the project ID carefully because it is permanent; do not put personal or security data in project/resource names. A billing account is selected only if applicable to the project setup; no payment configuration is part of the current verification work. [Create projects in Google Cloud](https://docs.cloud.google.com/resource-manager/docs/creating-managing-projects)
2. **Set up the consent screen and branding.** Add the app name, developer contact, authorized domain, homepage, and privacy policy. The setup flow for this project required accepting Google's API Services User Data Policy; that policy governs use of Google user data. Verify the domain in Search Console using an account with Owner or Editor access on the GCP project. Keep the homepage, Play listing, app, and consent screen branding consistent. [Google API Services User Data Policy](https://developers.google.com/terms/api-services-user-data-policy) · [Google verification requirements](https://support.google.com/cloud/answer/13464321?hl=en) · [Search Console ownership verification](https://support.google.com/webmasters/answer/9008080)
3. **Configure audience and scopes.** Use External audience for public users. While Testing, add only the intended test accounts; before production access, publish the app and submit the restricted `gmail.readonly` scope for verification. Publishing removes the test-user gate but does not itself approve the app or remove Google's unverified-app warning. The Testing user cap and the lifetime grant cap are separate controls; confirm the current limits in the Console. [Google OAuth FAQ](https://support.google.com/cloud/answer/13463817?hl=en) · [Submitting an app for verification](https://support.google.com/cloud/answer/13461325?hl=en)
4. **Enable the Gmail API and create the platform clients the app needs.** Register Web, Android, and iOS OAuth clients as required by the app. Register Android with the production package and Play App Signing SHA-1, and register iOS with the production bundle identifier. Keep the Web client ID in `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID`; iOS also needs `EXPO_PUBLIC_GOOGLE_IOS_CLIENT_ID`. These IDs are public identifiers, not secrets. [Google Android client authentication](https://developers.google.com/android/guides/client-auth?hl=en) · [Google's Sign in with Google best practices](https://developers.google.com/identity/siwg/best-practices)
5. **Keep credentials out of app code.** Do not put OAuth client secrets or service-account private keys in the client app or source control. Use only the public client IDs in the app's public environment configuration. This setup does not require configuring payment for the current verification submission.

## CASA and restricted-scope facts

Because `gmail.readonly` is restricted, Google requires an **annual security assessment**. Google's documentation says this assessment is the final step after the other verification requirements, and Google Trust and Safety will contact the developer when it is time to initiate it. CASA uses risk-based assurance levels that can depend on user count, requested scopes, and other app-specific signals; the required level may change over time. [Google Security Assessment](https://support.google.com/cloud/answer/13465431?hl=en)
