# Local foundations before online backup

Scope: the local V1 workflow and the gates before online backup.

[Key management](./key-management.md) is authoritative. V1 has one Device → User → Workplace hierarchy, one DEK per Workplace, and both independently saved recovery credentials. It uses the existing app lock; fresh biometric root authentication is not required. No readable DEK persists in storage.

## Delivered internal contracts

1. **Consistent capture.** A WatermelonDB reader holds source capture together. Plaintext ZIP export and single-Workplace snapshots use it; compression/encryption run after release. Copied MMKV preferences are not a cross-store transaction.
2. **Strict source snapshot.** Explicit tables/fields, schema 35, capture time, stable financial IDs, currency precisions and spending horizon. Parsing rejects unsupported formats, unknown fields, invalid primitives/enums, duplicate identities and broken references. Serialized plaintext is bounded to 32 MiB/100,000 source records.
3. **Scope/privacy.** Financial source records and audit history travel; derived balances, rate caches, pending Device SMS, Device switches and navigation preferences do not. Explicit SMS sources are omitted and structured metadata/audits use privacy sanitizers. Arbitrary user-authored text is not promised to be automatically detected.
4. **Local User enrollment.** Independent User and Device X25519 encryption pairs and a User Ed25519 signing pair; versioned public identity pin covers both User key roles; Device private key in the User/Device-scoped native vault; local Device-encrypted User bundle; independent User-recovery recipient and encrypted package. The downloadable credential must reopen the staged package and verify the same User/key pair before readiness.
5. **Local Workplace enrollment.** Explicit creation or local-upgrade generates one random DEK, its User-addressed member envelope and its independent Workplace-dump recovery envelope. Save/readback confirmation proves both envelopes yield the same DEK. Repeated enrollment refuses replacement; normal backup never generates keys.
6. **Storage/unlock.** Only Device private keys persist as vault-protected secrets, opened only by native code. Public metadata and encrypted envelopes live in immutable private files with small nonsecret AsyncStorage locators. Device-only vault loss does not hide surviving ciphertext; the caller loads an independently retained encrypted package and passes it to native User recovery. The app shell supplies existing app-lock state to the JS coordinator and native module; absent/locked policy fails closed. No persistent User-private-key/DEK cache exists; neither crosses the JS boundary. Failed writes retain explicit partial state; unconfirmed setup may be deliberately discarded before established data depends on it.
7. **Recovery separation.** User recovery reconstructs the same root onto independent Device keys and opens existing member envelopes. It supplies no online registration/membership change. Workplace dump creation/decryption carries recovery DEK envelope plus encrypted snapshot and returns readable data only. It cannot publish old tenancy or recover owner authority. The hosted download/support API is not implemented.
8. **Payload encryption.** The initial format 1 is AES-256-GCM ciphertext/routing only, binding the stable DEK fingerprint. Recovery secrets and wrappers are absent. Fresh local-writer encryptions reserve durable usage before execution, including abandoned attempts; re-exporting retained ciphertext spends no new budget. Exhaustion at 2^20 stops encryption while leaving reads available.
9. **Financial publication.** User-chain restore preserves shared IDs and commits a SHA-256 restore receipt with the graph. Exact retries do not duplicate rows/audits. Existing different books and cross-Workplace record collisions fail. Posted journals must balance; currency precision must match. Emergency dumps use a future import-as-copy handoff instead.
10. **Integration boundaries.** Human local encryption setup and fresh-install User recovery are wired. Online coordinator, HTTP transport, consent/outbox stores and their tests are deferred to a later PR; no online endpoint setting or backend exists. Signed registration/manifest provisioning and schema admission remain required. No SQL deployment contract is delivered.
11. **Human setup and recovery.** Settings and privacy-gated welcome recovery use the existing app shell. Export separate User and Workplace secrets plus a User-signed encrypted package; readiness requires reopening saved files. Public-only intent/identity checkpoints support resume and explicit unfinished-step discard. Same-User recovery validates secret and signature before mutation, retains existing books/preferences under a matching local key binding, and restores missing books with original financial IDs. It finishes the satisfied empty-device creation gate and never resets uncertain usage or transfers writing authority. Unfinished package references can be explicitly abandoned to recover from a missing file; keys and consumed usage stay intact. Device-access removal requires verified export; retained ciphertext remains usable without the missing Device key. Native file adapters use direct Android document export and short-lived, cleaned-up iOS copies.

## Native key-operation boundary

`ExpoKeyCrypto` is a local Expo module with one shared C++ implementation, thin Kotlin/Objective-C++/Swift adapters and native vault/file access. It reuses QuickCrypto’s pinned OpenSSL 3.6.2 provider on both platforms; HPKE remains X25519/HKDF-SHA256/AES-256-GCM. JSON transport uses the unmodified nlohmann/json 3.12.0 single header, committed with its upstream MIT license and a pinned SHA-256 under `modules/expo-key-crypto/vendor`. Native builds verify it locally; there is no build-time header download. GitHub marks it as vendored source. Tests create disposable keys and data for the current format; no real credential or generated build binary is retained.

JS uses explicit key generation/opening, reference-based signing/encryption/decryption and recipient wrapping, scoped vault presence/removal and purpose-specific recovery operations. Only public metadata, ciphertext, opaque references and application plaintext cross the transport. There is no raw-key read/write or key-borrow callback. Native recovery-file import/export gives JS only an expiring process-local handle. A bounded native handle cache retains pending recovery files until import/use, cleanup or expiry; an explicit export lease spans the OS picker/share transition. Root keys and DEKs remain operation-scoped. Controlled buffers are wiped; this is ordinary native app memory, with no enclave, separate-process or complete-memory-erasure guarantee.

Public creation intent is checkpointed before native generation. Android uses an independent AndroidKeyStore alias, scope-bound encrypted preferences and explicit backup exclusions; iOS uses its dedicated Keychain service. JS owns durable invocation reservations, per-Workplace verified bindings, snapshot validation and book publication. Coordinator/restore regressions call the real C++ engine. An AES-256-GCM known-answer test and an independent HPKE/AES consumer verify the current implementation. Source and production-bundle guards reject native test-support imports in the application.

Run `bun run test:native-key-crypto` for the real-C++ host lane, also required by `bun run verify` and the dedicated macOS CI job. The runner uses the configured `CXX` or `c++`, discovers HPKE-enabled OpenSSL through pkg-config/Homebrew, or accepts `FFB_OPENSSL_PREFIX`; missing prerequisites fail rather than silently skipping native tests. Standard Jest and native suites are distinct. Native tests retain the meaningful recovery, collision and invocation regressions while using production coordinator code. Native app builds are required to install the module; an absent module fails closed without a JS crypto fallback.

The shared core is split into crypto primitives, protocol envelopes, snapshot cryptography and the key engine. Public operations call focused handlers directly; request/operation rewriting is removed. Native snapshot header checks use SAX parsing of the complete JSON syntax with a 64-level nesting bound. They retain only Workplace ID and integer schema version, reject duplicate header fields and preserve checks against authenticated routing. Encryption reads the input bytes directly instead of copying the plaintext into a second buffer. The 32 MiB snapshot cap remains.

Native bridges return allowlisted error codes rather than exception text. The recovery UI explains locked keys, missing key material, invalid/mismatched files, expired handles and Workplace collisions, and logs only the code. Its reducer tracks view/operation state while one transient holder retains native handles; background, lock and blur abort the recovery signal. The service checks cancellation at mutation boundaries, and the publication signal reaches the database writer so a cancelled queued restore cannot publish later. A started atomic batch completes rather than leaving partial books. A receipt-bound public completion checkpoint resumes spending preferences, Device registration and the unchanged setup gate after lock/background or process restart. Uncertain imported encryption usage is always exhausted, even without its old marker. Device-access removal checks separately confirmed packages for all enrolled Workplaces. The native registry mutex, per-store hierarchy queue and setup-workflow queue retain their separate responsibilities. Bounded collision counts run inside the WatermelonDB writer, preserving admission/publication ordering without hydrating books. Workplace dump verification remains a local V1 contract; its hosted download/support API remains deferred.

The iOS provider binding still uses QuickCrypto 1.1.7's private OpenSSL header/symbol-prefix layout. Installation checks its package version, HPKE header and pinned prefix-header hash and fails clearly if the binding changes. This dependency is explicit; moving to an independent iOS OpenSSL provider remains separate build/dependency work.

Shared `services/setup` modules own draft storage/parsing, prepared restore state, pending creation IDs, launch projection and recovery completion. The Setup feature owns its journey recipes, UI and coordinator; Settings calls the shared completion service directly.

Android backup and data-extraction rules exclude only `FFBKeyCrypto.xml`, preserving default coverage of local books and MMKV preferences. They contain no `<include>` entries because those would restrict coverage to explicitly listed domains. The app manifest and Expo config plugin select the owned rules. Real Google backup and phone-to-phone transfer remain release gates.

Detox simulator builds use ad-hoc signing for native Keychain tests, without distribution credentials. Release test builds disable both Sentry artifact-upload paths; device signing is configured separately.

## Verification and remaining gates

Run `bun run verify` for app/coordinator tests, the real-C++ lane, types, architecture, privacy and lint. Tests generate current-format credentials/envelopes rather than preserving intermediate implementations.

Automated checks cover the local key chain, signed recovery packages, strict parsing, snapshot accounting/privacy boundaries, original-ID restore and exact retries, app-lock changes, storage failures and encryption usage. Recovery regressions cover retained books/preferences after Device-access removal, completion of the empty-device setup gate, missing pending package files, repeated collision rejection and interrupted recovery after setup-checkpoint loss. Preservation requires a verified binding for the selected Workplace and DEK fingerprint, recorded by completed local enrollment or successful publication. Recovering B cannot authorize surviving imported keys for A; unverified positive pending decisions cannot establish bindings. Negative provenance is saved before recovering User access. Failed enrollment checkpoints resume through explicit saved-credential verification on the original writer Device. Starting recovery drops an old unconfirmed export reference and cleans unreferenced internal ciphertext without reclaiming its consumed budget. Publication precedes package confirmation.

The native proof is opt-in through an explicit `FFB_RECOVERY_ROLE`, separate from default Detox runs. Native fixture-file APIs require an E2E compile capability (Android build configuration / iOS `FFB_KEY_CRYPTO_E2E` Swift condition); ordinary builds expose only native-owned secret pickers. The native proof covers current-format creation/signing/tamper rejection, restart, installation loss, missing Device keys and orphan keys. Simulator/emulator results do not close physical iPhone/Android, real picker/share, storage-denial/corruption or complete interruption gates. Validate both native platform builds before release. Android/iOS interoperability must preserve the same User, signing identity, DEK and financial records. Ordinary native memory and filesystem deletion do not guarantee complete erasure.

Two earlier Android builds used `SENTRY_DISABLE_AUTO_UPLOAD=1`; the installed integration requires the literal `true`. They uploaded JavaScript/source maps to Sentry project `full-frills-balance / react-native`, release `in.sahilsoni.fullfrillsbalance@1.0.0+1`, distribution 1. Recovery phrases and generated financial fixtures were not part of those artifacts. Bundle IDs `9a64ad56-a282-5ec3-8023-d9c69ee99281` and `9cee3dbf-a88e-5349-aa5b-aceee7d2ca0e` remain pending user-authorized deletion. E2E Release builds now set both upload-disable flags to `true`; no external deletion or backend provisioning occurred.

2. Extend current simulator/AVD proof to physical iOS/Android and both transfer directions. Exercise restart/reinstall, app lock/background, missing/corrupt vault entries, storage denial, cancellation and kill-before/after each durable write. Prove file/pointer durability, cleanup and memory bounds on physical devices.
3. Bind the same UUID to online login; implement signed Device registration, initial manifests, User/member/recovery-envelope delivery, backend authorization/challenges, consent, durable publication and authenticated checkpoints. Define explicit single-writer handover rather than resetting invocation usage on replacement.
4. Define supported snapshot-schema evolution before enabling cloud persistence. The initial encrypted snapshot format is 1; unsupported versions are rejected.
5. Release manual online backup only after the real same-User replacement path succeeds end to end. A Workplace ID/support lookup locates dump ciphertext; it does not supply a decryption secret or grant authority.
6. Before concurrent editing/sharing, implement revisions/conflicts, durable mutations/receipts/cursors, tombstone retention, mixed-version behavior, disjoint signed budgets and verified invitations. Review rotation/root replacement separately; there is no working V1 rotation API.

Ordinary local SQLite and plaintext ZIP exports retain their existing behavior. Automatic backup, paid tiers and cloud vendor changes remain outside this work.
