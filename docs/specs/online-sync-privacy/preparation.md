# Local foundations before online backup

Scope: the local V1 workflow and the gates before online backup.

[Key management](./key-management.md) is authoritative. V1 has one Device → User → Workplace hierarchy, one DEK per Workplace, and both independently saved recovery credentials. It uses the existing app lock; fresh biometric root authentication is not required. No readable DEK persists, even in SecureStore. The Supabase placeholder contracts have been removed.

## Delivered internal contracts

1. **Consistent capture.** A WatermelonDB reader holds source capture together. Legacy ZIP export and single-Workplace snapshots use it; compression/encryption run after release. Copied MMKV preferences are not a cross-store transaction.
2. **Strict source snapshot.** Explicit tables/fields, schema 35, capture time, stable financial IDs, currency precisions and spending horizon. Parsing rejects unsupported formats, unknown fields, invalid primitives/enums, duplicate identities and broken references. Serialized plaintext is bounded to 32 MiB/100,000 source records.
3. **Scope/privacy.** Financial source records and audit history travel; derived balances, rate caches, pending Device SMS, Device switches and navigation preferences do not. Explicit SMS sources are omitted and structured metadata/audits use privacy sanitizers. Arbitrary user-authored text is not promised to be automatically detected.
4. **Local User enrollment.** Independent User and Device X25519 encryption pairs and a User Ed25519 signing pair; versioned public identity pin covers both User key roles; Device private key in the User/Device-scoped native vault; local Device-encrypted User bundle; independent User-recovery recipient and encrypted package. The downloadable credential must reopen the staged package and verify the same User/key pair before readiness.
5. **Local Workplace enrollment.** Explicit creation or local-upgrade generates one random DEK, its User-addressed member envelope and its independent Workplace-dump recovery envelope. Save/readback confirmation proves both envelopes yield the same DEK. Repeated enrollment refuses replacement; normal backup never generates keys.
6. **Storage/unlock.** Only Device private keys persist as vault-protected secrets, opened only by native code. Public metadata and encrypted envelopes live in immutable private files with small nonsecret AsyncStorage locators. Device-only vault loss does not hide surviving ciphertext; User recovery reads an independently retained package through an injected provider-neutral source. The app shell supplies existing app-lock state to the JS coordinator and native module; absent/locked policy fails closed. No persistent User-private-key/DEK cache exists; neither crosses the JS boundary. Failed writes retain explicit partial state; unconfirmed setup may be deliberately discarded before established data depends on it.
7. **Recovery separation.** User recovery reconstructs the same root onto independent Device keys and opens existing member envelopes. It supplies no online registration/membership change. Workplace dump creation/decryption carries recovery DEK envelope plus encrypted snapshot and returns readable data only. It cannot publish old tenancy or recover owner authority. The hosted download/support API is not implemented.
8. **Payload encryption.** Format 2 is AES-256-GCM ciphertext/routing only, binding the stable DEK fingerprint. Recovery secrets and wrappers are absent. Fresh local-writer encryptions reserve durable usage before execution, including abandoned attempts; re-exporting retained ciphertext spends no new budget. Exhaustion at 2^20 stops encryption while leaving reads available.
9. **Financial publication.** User-chain restore preserves shared IDs and commits a SHA-256 restore receipt with the graph. Exact retries do not duplicate rows/audits. Existing different books and cross-Workplace record collisions fail. Posted journals must balance; currency precision must match. Emergency dumps use a future import-as-copy handoff instead.
10. **Integration boundaries.** Human local encryption setup and fresh-install User recovery are wired. Online coordinator, HTTP transport, consent/outbox stores and their tests are deferred to a later PR; no online endpoint setting or backend exists. Signed registration/manifest provisioning and schema admission remain required. No SQL deployment contract is delivered.
11. **Human setup and recovery.** Settings and privacy-gated welcome recovery use the existing app shell. Export separate User and Workplace secrets plus a User-signed encrypted package; readiness requires reopening saved files. Public-only intent/identity checkpoints support resume and explicit unfinished-step discard. Same-User recovery validates secret and signature before mutation, retains existing books/preferences under a matching local key binding, and restores missing books with original financial IDs. It finishes the satisfied empty-device creation gate and never resets uncertain usage or transfers writing authority. Unfinished package references can be explicitly abandoned to recover from a missing file; keys and consumed usage stay intact. Device-access removal requires verified export; retained ciphertext remains usable without the missing Device key. Native file adapters use direct Android document export and short-lived, cleaned-up iOS copies.

## Native key-operation boundary

`ExpoKeyCrypto` is a local Expo module with one shared C++ implementation, thin Kotlin/Objective-C++/Swift adapters and native vault/file access. It reuses QuickCrypto’s pinned OpenSSL 3.6.2 provider on both platforms; HPKE remains X25519/HKDF-SHA256/AES-256-GCM. JSON transport uses the unmodified nlohmann/json 3.12.0 single header, committed with its upstream MIT license and a pinned SHA-256 under `modules/expo-key-crypto/vendor`. Native builds verify it locally; there is no build-time header download. GitHub marks it as vendored source. A synthetic public test vector is committed; no real credential or generated build binary is retained.

JS uses explicit key generation/opening, reference-based signing/encryption/decryption and recipient wrapping, scoped vault presence/removal and purpose-specific recovery operations. Only public metadata, ciphertext, opaque references and application plaintext cross the transport. There is no raw-key read/write or key-borrow callback. Native recovery-file import/export keeps the original externally saved credential format but gives JS only an expiring process-local handle. A bounded native handle cache retains pending recovery files until import/use, cleanup or expiry; an explicit export lease spans the OS picker/share transition. Root keys and DEKs remain operation-scoped. Controlled buffers are wiped; this is ordinary native app memory, with no enclave, separate-process or complete-memory-erasure guarantee.

Public creation intent is checkpointed before native generation. The feature has not been released or distributed, and there is no development data to migrate. Native vaults own their storage and have no prototype SecureStore readers. Android uses an independent AndroidKeyStore alias, scope-bound encrypted preferences and explicit backup exclusions; iOS uses its dedicated Keychain service. JS continues to own durable invocation reservations, per-Workplace verified bindings, snapshot validation and book publication. The previous JS crypto implementation is deleted. Frozen V1 vectors replace it; required coordinator/restore regressions call the real C++ engine. Obsolete raw-key callback and JS-adapter parity tests are removed, and duplicate budget/interruption tests are consolidated. Source and production-bundle guards reject native test-support imports in the application.

Run `bun run test:native-key-crypto` for the real-C++ host lane, also required by `bun run verify` and the dedicated macOS CI job. The runner uses the configured `CXX` or `c++`, discovers HPKE-enabled OpenSSL through pkg-config/Homebrew, or accepts `FFB_OPENSSL_PREFIX`; missing prerequisites fail rather than silently skipping native tests. Standard Jest and native suites are distinct. Native tests retain the meaningful recovery, collision and invocation regressions while using production coordinator code. Native app builds are required to install the module; an absent module fails closed without a JS crypto fallback.

The iOS provider binding still uses QuickCrypto 1.1.7's private OpenSSL header/symbol-prefix layout. Installation checks its package version, HPKE header and pinned prefix-header hash and fails clearly if the binding changes. This dependency is explicit; moving to an independent iOS OpenSSL provider remains separate build/dependency work.

## Verification and remaining gates

Current host checks after the key-reference reshape: **538 application suites, 3,791 tests and 9 snapshots passed**. The separate real-C++ lane passed **five suites and 58 tests**, including the key/recovery coordinator regressions, frozen V1 vectors and direct reference-security tests. Application/E2E types, architecture/privacy guards and lint passed; lint has zero errors and one existing journal-hook warning. The production Android export passed E2E/test-support exclusion guards after the reshape, using one worker. The app and vault Android test builds passed offline with the pinned vendored header. APK resources confirm the manifest selects the owned backup/data-extraction rules. The installed Android app passed creation/signature/tamper validation, process restart and actual uninstall/reinstall recovery. The current iOS simulator Release build passed, and Android-created files recovered on a fresh isolated iOS simulator with the same signing identity, every source record and safe retries. These simulator/AVD results do not close physical-device, real-picker or complete interruption gates.

The clean Android vault passed **six instrumented cases using actual AndroidKeyStore**, rerun against the current vault test build: independent owned storage, replacement refusal, authenticated scope binding, missing wrapping key without regeneration, malformed records and scoped removal. The ownership test fails against the old SecureStore-coupled vault and passes against the new implementation. A full Android release build stopped at optimization under a 1.5 GiB heap cap; the sequential retry completed app release packaging but its broad all-module test target encountered an uncached, unrelated Expo Updates test dependency in offline mode. The app and owned vault targets then passed offline. Validation ran sequentially with one build worker, one native compiler worker and one JS worker. Parallel native builds/emulators are avoided after a host crash.

Automated checks cover the local key chain, signed recovery packages, strict parsing, snapshot accounting/privacy boundaries, original-ID restore and exact retries, app-lock changes, storage failures and encryption usage. Recovery regressions cover retained books/preferences after Device-access removal, completion of the empty-device setup gate, missing pending package files, repeated collision rejection and interrupted recovery after setup-checkpoint loss. Preservation requires a verified binding for the selected Workplace and DEK fingerprint, recorded by completed local enrollment or successful publication. Recovering B cannot authorize surviving imported keys for A; legacy positive pending decisions cannot establish bindings. Negative provenance is saved before recovering User access. Failed enrollment checkpoints resume through explicit saved-credential verification on the original writer Device. Starting recovery drops an old unconfirmed export reference while retaining its file and consumed budget. Publication precedes package confirmation.

Shared `services/setup` modules now own the draft model/parser/store, prepared-restore cache, pending creation ID, launch projection and recovery completion. Setup keeps its journey recipes, UI and coordinator, with compatibility re-exports for existing callers. Settings recovery calls the shared completion service directly; the Settings → Setup feature exception is removed. Draft storage keys and schema are unchanged.

The previously pushed native implementation (`02a86884c`) passed six Android key/package cases and six iOS simulator cases, including Android-to-iOS replacement and actual uninstall/reinstall, plus the normal-app setup/recovery entry tests. Those runs covered the earlier vault implementation and dispatcher; they are historical evidence, not validation of the new clean vault or key-reference API. Physical-device, real-picker and complete interruption gates remain open.

Earlier UI verification required replacing an unsupported Detox matcher with native element attributes. In the new native run, the proof screen initially lacked app-shell unlock policy and correctly failed closed; the explicit test-only proof policy fixed the harness. A System UI ANR dialog blocked the second AVD's focus until dismissed, after which replacement passed. iOS app linking initially exposed an omitted shared C++ source; the local pod now includes it through an Objective-C++ compilation unit. The iOS entry test initially checked the UIView interaction flag instead of the React Native disabled accessibility trait; checking `notEnabled` fixed that platform-specific assertion. OS file-picker/share tests use mocked surfaces. Physical iPhone/Android and cross-platform physical recovery, complete real-picker saved-file round trips, app-lock/background behavior, memory limits and the full interruption/storage-denial/corruption matrix remain open. Simulator proof does not establish physical Keychain/device-transfer behavior. Pairing/QR and signed online enrollment are absent; replacement is recovery-only. Dated review reports and per-run evidence are omitted from this change set.

The local module supplies Android backup/data-extraction rules excluding only `FFBKeyCrypto.xml` and `SecureStore.xml`. The app manifest and Expo config plugin select those rules. All three policies (Android 11 and earlier backup, Android 12+ cloud backup and device transfer) retain default app-file/database coverage, including local books and MMKV preferences. They intentionally have no `<include>` entries: [Android's documented inclusion rules](https://developer.android.com/identity/data/autobackup) make any include a whitelist that excludes unlisted domains. SecureStore no longer owns the native Device-key storage contract. Five regression checks verify the selected XML policies, manifest and Expo regeneration; they fail on the old policies and pass with exclusions only. Android resource compilation and all 37 script tests pass; real Google backup and phone-to-phone transfer remain untested.

The Detox iOS simulator build intentionally uses ad-hoc signing to give Keychain/SecureStore proof tests a signing identity. It uses no distribution credentials and does not change physical-device signing. This setting is documented in the configuration; signing alone is not evidence that physical-device gates passed.

Define explicit single-writer handover rather than resetting invocation usage on replacement.
4. Define supported snapshot-schema evolution and older-backup fixtures before enabling cloud persistence. Format-1 proof fixtures were unreleased and are intentionally rejected.
5. Release manual online backup only after the real same-User replacement path succeeds end to end. A Workplace ID/support lookup locates dump ciphertext; it does not supply a decryption secret or grant authority.
6. Before concurrent editing/sharing, implement revisions/conflicts, durable mutations/receipts/cursors, tombstone retention, mixed-version behavior, disjoint signed budgets and verified invitations. Review rotation/root replacement separately; there is no working V1 rotation API.

Ordinary local SQLite and plaintext ZIP exports retain their existing behavior. Automatic backup, paid tiers and cloud vendor changes remain outside this work.
