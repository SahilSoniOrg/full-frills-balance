# Repository Layer Map

This map describes the persistence owners after the repository-layer refactor. It is a guide to where behavior belongs, not a requirement to create one repository per table.

## Ownership and contracts

| Data and owner                                                                                                                       | Inputs and outputs                                                                                                                                                                                                                 | Write boundary                                                                                                                                                        | Main callers                                                                                                            | Persistence role and invariants                                                                                                                                                                                                                 |
| ------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Account** — `account/AccountQueryRepository`, `AccountObserveQueries`, `AccountWriteRepository`                                    | Workplace-scoped IDs and `AccountFilter`; fetch returns models or `null`, observations return RxJS models, writes accept `AccountPersistenceInput` / normalized mutation plans and return account plus commit facts.               | `AccountingWriteSession`; required audit records are staged in the same batch. `AccountTreeTransactionCoordinator` serializes hierarchy plans.                        | Account commands, account screens, account reference checks, reporting and ledger workflows.                            | Source of truth. Workplace and deleted-row clauses are shared by `accountFilters.ts`; observable columns remain owned by each observer. Type changes report balance-rebuild IDs after commit. Hierarchy validation stays in commands/workflows. |
| **Journal aggregate** — `journal/JournalPersistenceRepository`                                                                       | Typed journal put/patch, lifecycle and cross-journal inputs; returns journal results, affected accounts, and rebuild impact. Journal reads use `journalQueryRepository`; timeline observers and enrichment have dedicated modules. | One accounting write session covers journal, transaction legs, metadata, required audit and linked records.                                                           | Journal commands/services; timeline, SMS, reports, planned-payment and integrity queries use their specialized readers. | Source of truth. Transaction rows are ledger legs and have no standalone CRUD lifecycle. | **Transactions** — `transaction/TransactionQueryRepository`, `TransactionObserveQueries`, `TransactionWriteRepository`               | Workplace-scoped lookup/filter inputs and transaction models; ID/journal batch reads use bounded chunking with requested chunk order and database order within each chunk.                                                         | Ledger writes go through journal persistence; `TransactionWriteRepository` prepares projection updates for owning rebuild workflows.                                  | Journal and account queries, reports, budgets, simulation and rebuild.                                                  | Transaction rows are journal-owned source data. | **Planned payments** — `PlannedPaymentRepository`                                                                                    | Typed create input, `PlannedPaymentScheduleUpdate`, scoped lookups, and occurrence-only status/cursor updates. Occurrence identity and schedule advancement are coordinated atomically. `updateSchedule` cannot change occurrence status.                                                 |

Rule normalization and action-column synchronization remain local to this owner; matching/execution stay in SMS services.                                                                                                 |

Historical/cache cleanup is maintenance; rates are not a substitute for journal FX values.                                                                                                    |
| **Balance snapshots / running balances** — `BalanceSnapshotRepository`, `TransactionRawRebuildQueries`, `TransactionWriteRepository` | Scoped account/date queries, rebuild rows and prepared projection updates.                                                                                                                                                         | Rebuild workflow batches transaction balance updates, snapshot invalidation/recreation and any repair audit.                                                          | `AccountingRebuildService`, balance reads and integrity verification/repair.                                            | Disposable projections. | **Database/workplace lifecycle** — `DatabaseRepository`, `WorkplaceRepository`                                                       | Reset/purge table lists, workplace identity and setup inputs.                                                                                                                                                                      | Lifecycle owners control their writers and privileged adapter/cache synchronization. Workplace creation with starter accounts publishes both together.                | Setup, restore, settings, factory reset and integrity maintenance.                                                      | Privileged infrastructure. These operations are intentionally outside ordinary entity CRUD; irreversible cleanup stays explicit.                                                                                                                |

## Shared mechanics and raw-query ownership

| Module                                                                     | Contract                                                                                                                                                                         |
| -------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `AccountingWriteSession`                                                   | One WatermelonDB writer and one final batch for typed cross-repository accounting changes. Deferred operation factories are prepared immediately before batching.                |
| `persistBatch`                                                             | Simpler prepared-operation batch for bounded non-ledger workflows that do not need accounting-session facts or staging. Do not use it as a competing path for ledger invariants. |
| `fetchSequentiallyInChunks`                                                | Bounds WatermelonDB `oneOf` query size, preserves requested chunk order, and preserves database order inside each chunk. It does not promise per-ID ordering inside a chunk.     |
| `account/accountFilters.ts`                                                | Shared workplace, deleted-row, type, parent, ID, name and ordering clauses. Fetch and observe APIs stay separate so observation columns are not lost.                            |
| `raw/RawSqlExecutor`                                                       | Only raw adapter read seam; applies row-key normalization and propagates SQL failures. It does not own SQL statements or domain result shapes.                                   |
| `account/AccountLedgerMetricsQueries`                                      | Account ledger period aggregates and unreconciled observations, including ORM fallback where needed.                                                                             |
| `raw/TransactionRawMetricsQueries`                                         | Named transaction count/balance/delta metrics.                                                                                                                                   |
| `raw/TransactionRawRebuildQueries`                                         | Named balance rebuild aggregates and source rows.                                                                                                                                |
| `raw/TransactionRawPatternQueries`                                         | Named recurring-pattern projection query.                                                                                                                                        |
| `transaction/TransactionInsightQueries`                                    | Typed insight transaction projection.                                                                                                                                            |
| `journal/JournalEnrichmentQueries` and `journal/journalBalanceLineQueries` | Typed journal-facing enrichment and balance-line projections.                                                                                                                    |

`DatabaseUtils` is the adapter bridge. `DatabaseRepository` retains direct raw access only for privileged workplace purge, with WatermelonDB cache synchronization. Production features and services must use named query modules; `TransactionRawRepository` is removed. Schema migrations remain a separate infrastructure exception.

## Operational rules

- Workplace-owned read/write APIs take a `WorkplaceId`; global currency/rate data and database lifecycle are explicit exceptions.
- Missing rows return `null` or a documented no-op only when that is the operation's contract. Database errors must not be converted into not-found results.
- Deleted-row inclusion, journal status sets, sort order, chunking and observer columns are part of each query's contract.
- Journal and transaction-leg writes stay in one accounting boundary. Audit and required inbox/schedule changes join that batch.
- Rebuild, cache invalidation and analytics are dispatched only after the durable write succeeds.
- Projections are rebuildable; business decisions read source-of-truth journal/account/configuration data.
- Prefer an entity-local typed CRUD method for local lifecycle operations. Keep cross-record business rules in commands/workflows and do not add a generic `Repository<T>`.
